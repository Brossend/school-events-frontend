# FE-005 — Interactive Scenario Constructor

Дата: 26 октября 2026, Asia/Yekaterinburg. **Статус: PENDING INDEPENDENT REVIEW.**

## Реализация

`/constructor` заменяет заглушку общим пятишаговым wizard. Шаги соответствуют Figma: событие; участники; формат; цели и ресурсы; проверка данных. Назад и ссылки «Изменить» сохраняют значения. Обязательные поля проверяются до перехода, полный DTO — перед POST. Ошибки сервера возвращают пользователя на соответствующий шаг, ссылки в сводке ошибок фокусируют контроль поля. Native radio/checkbox, fieldset/legend, связанные labels, aria-current, disabled/loading и управление фокусом доступны с клавиатуры. UiField/UiTextarea получили необязательный согласованный id для labels и возврата к ошибке; прежнее поведение без id сохранено.

Повод — discriminated union: ровно custom title, calendar event или tradition version. DTO строится явным whitelist; school_id отсутствует в JSON. Диапазоны соответствуют CreateScenarioRequestDTO: классы 1–11, численность 5–500, длительность 20–240, название 3–255, ресурс до 255 символов, ограничения до 1000. Принимаются три масштаба, шесть форматов и шесть направлений, одно направление за раз. Ресурсы необязательны; семья — действительный boolean, а не фиктивное согласие.

Календарь загружается через реальный API с поиском и пагинацией. Версии традиций берутся из списка текущей школы, произвольный foreign UUID не становится выбором. Ссылки из preview календаря, карточки события и ежегодной версии содержат школу и ID; главная открывает чистый конструктор. При несовпадении школы ссылка очищается. Произвольные календарные ID разрешаются через GET и затем проходят окончательную серверную проверку видимости/статуса.

На последнем шаге один POST создаёт ScenarioRequest; затем выполняется настоящий GET. Подтверждение показывает ID и ссылку `/scenario-requests/:id`. Страница ссылки также выполняет GET и проверяет совпадение school_id. Генерация, очередь, polling и результаты не имитируются. FE-006 не реализован.

## Контрактные наблюдения

Операции: `POST /api/v1/scenario-requests` → 201 и `GET /api/v1/scenario-requests/{id}` → 200. Школа определяется авторизацией и X-School-Id. Реальные JSON запросов, ответов POST и GET приложены в [http-mutations.json](fe005/evidence/http-mutations.json); заголовки Cookie/XSRF и пароли не сохранялись.

OpenAPI требует created_at в ScenarioRequestEnvelope, но фактический POST не возвращает его: значение заполняется БД и появляется в следующем GET. Поэтому UI не использует отсутствующую дату POST и показывает перечитанное состояние. OpenAPI объявляет context_snapshot как пустой generic object; сервер отдаёт вложенный снимок школы, пользователя, повода и параметров. Он отображается как неизменяемый серверный JSON без вымышленных полей. generated types и backend не изменялись. Долг контракта: описать snapshot и разные POST/GET envelopes либо возвращать refreshed модель из POST на отдельном backend-этапе.

Проверено фактически: чужая версия традиции и чужое школьное событие дают 403. Федеральный draft, недоступный через visibleTo, также даёт 403 до проверки статуса; не всякий draft даёт 422. В существующем backend-тесте видимый draft школьного события доходит до 422 EVENT_STATUS_INVALID. Это разные ветви, UI показывает действительное сообщение сервера. Незнакомый ID GET даёт 404. GET своей школы доступен автору или администратору школы/системы, не другому teacher. Серверное RBAC остаётся определяющим.

Сохранены прежние документы и ограничения `/auth/me`, календаря, provenance и ежегодных версий. Настройки/зависимости Nuxt не откатывались, новые пакеты не устанавливались; package.json и package-lock.json включаются в поставку.

## Отмена, tenant и неизвестный результат

Черновик хранится только в памяти страницы. Смена пользователя/школы очищает поля, результаты и ошибки; read-запросы отменяются и устаревший ответ отбрасывается по контексту. При logout защищённые маршруты используют прежние guards. Перед POST фиксируется текущая школа и передаётся X-School-Id, не school_id в body.

Кнопка блокируется синхронно до первого await. В sessionStorage сохраняется только квитанция состояния sending/uncertain/saved и ID, отдельно для user+school; частные поля черновика туда не записываются. После перезагрузки sending становится uncertain. Сеть, 5xx или неполный успешный ответ блокируют повтор; автоматически POST не повторяется. 4xx возвращает редактируемую форму, при 422 значения сохранены. Полученный ID используется для GET; ошибка GET не инициирует новый POST.

Backend не предлагает idempotency key и список/поиск ScenarioRequest для восстановления потерянного ответа. Поэтому exactly-once между вкладками/устройствами не гарантируется. sessionStorage ограничен вкладкой; его очистка снимает локальную защиту. Для неизвестного результата UI предупреждает о возможной записи и предлагает сверить её с администратором; новая попытка разрешается только отдельным осознанным действием с предупреждением о дубликате. При недоступном storage отправка блокируется. Abort не откатывает уже принятую сервером транзакцию; квитанция старого контекста остаётся консервативной. Межвкладочная идемпотентность требует отдельного backend-контракта.

Docker пришлось восстановить после паузы из-за служебного сокета dockerInference; фабричный сброс, удаление данных или изменение backend не выполнялись.

## Ограничения и следующий этап

Нет сохранения/восстановления незавершённого черновика после ухода со страницы. Нет списка ScenarioRequest и восстановления потерянного ответа, серверной идемпотентности, редактирования сохранённого запроса, даты/площадки и генерации. Культурный snapshot не является подтверждением истинности фактов. Неизвестные сетевые результаты не выдаются за успешные записи.

План FE-006: сверить существующие generation/run/result endpoints и Figma; реализовать отдельный явный запуск с серверной идемпотентностью; cancellation/stale-context guards и ограниченный polling; действительные queued/running/completed/failed/timed_out состояния; чтение сценария и источников с ролью педагога; отдельные изолированные E2E и адаптивный аудит. Этот план не означает, что функциональность реализована в FE-005.
