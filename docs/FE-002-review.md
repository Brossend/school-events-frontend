## 3. Контракт API и существенные ограничения

Источник: `../school/docs/openapi.yaml`, существующие DashboardController, CalendarEventController и ListCalendarEventsRequest. Никаких backend-исправлений или mock-сервера не добавлялось.

1. **Календарь не получает даты событий.** И OpenAPI CalendarEventSummary/Envelope, и реальный list/detail JSON не содержат fixed_month/fixed_day, occurrences или start/end. В evidence сохранён реальный набор list keys: `id, title, event_type, region_code, description`. Следовательно, точные event markers внутри Figma-сетки не могут быть достоверно реализованы этим контрактом. Сетка сейчас работает как выбор календарного периода/дня: from/to передаются серверу, найденные события отображаются рядом/ниже. Распределение событий по дням не имитируется. На карточках явно написано «Точная дата недоступна». Это **известное функциональное отличие от полного Figma-календаря**, требующее отдельного согласования backend-контракта, а не скрытая готовая функция.
2. Dashboard summary возвращает fixed_month/fixed_day ближайших событий, поэтому на главной эти реальные ежегодные даты можно показать. Следующий год вычисляется только для презентации ежегодной даты, с обработкой 29 февраля и timezone Asia/Yekaterinburg; порядок событий и показатели берутся с сервера, не пересчитываются на клиенте.
3. Отдельные category/age/sort-параметры отсутствуют в OpenAPI. Доступны четыре event type и q/region_code/from/to/page/per_page. Только они отправляются в list API; month/view — исключительно UI URL-параметры. Неописанный `academic_year`, хотя встречается в backend request-классе, frontend не передаёт. Отдельного фильтра направления, возраста и сортировки нет; недоступность возрастного/тематического фильтра видна пользователю. Серверный порядок сохраняется.
4. DashboardSummaryDetail описывает элементы двух массивов только как `type: object`. Локальные UpcomingEvent/RecentScenario уточнены по действующему DashboardController; `parseDashboard` проверяет их структуру, даты, роли статуса и целые счётчики. Generated OpenAPI вручную не менялся, any не используется. Нарушенный ответ становится error state, а не демонстрационными карточками.
5. Расхождение `/auth/me` сохранено как интеграционная задача FE-001: OpenAPI UserEnvelope плоский, сервер возвращает user + schools. Существующий узкий parseSessionProfile остаётся, backend/spec не редактировались. Подробное сравнение — `FE-001-final-review.md`.
6. Полная карточка и проверка первоисточников остаются на FE-003. В текущем `/calendar/:id` показаны только базовые настоящие сведения. Просмотр источников/экспертизы не симулируется.
7. Конструктор и создание собственного события не входят в FE-002. Hero/preview ведут к уже существующему честному маршруту будущего конструктора; «Своё событие» объясняет недоступность, а не имитирует сохранение. Не отправляются POST создания/генерации.

Таким образом, поиск, период, выборка, пагинация и переходы работают реально; **полное соответствие расположению событий по дням Figma не заявляется** до расширения даты в backend response.

## 4. Изоляция школы и защита от гонок

- `createLatestResource` очищает data/error до нового запроса, abort предыдущего, сравнивает generation и контекст школы при success/error. Даже транспорт, игнорирующий abort, не применит старый результат.
- useSchoolResource реагирует на школу и query, сбрасывается при размонтировании/потере tenant. Layout FE-001 перемонтирует школьное содержимое по tenant key.
- API-клиент сохраняет schoolId в начале запроса, поддерживает AbortSignal и не вызывает глобальные callback ошибок после отмены/смены контекста. У локальных error/retry UI отключается дублирующее глобальное уведомление; актуальный 401 продолжает очищать сессию.
- selectSchool применяет только последнее актуальное подтверждение. Поздний ответ после clear/logout не восстанавливает школу; rejected switch не заменяет текущий подтверждённый tenant.
- В браузере выполнена настоящая смена школы на Гимназию №9; повторная главная получает её название из summary. Данные предыдущего tenant не используются как кэш новой школы.

Два используемых локальных tenant имеют одинаковые видимые показатели multi-school пользователя (0 сценариев, 1 традиция). Это не доказательство равенства наборов данных вообще: изоляция проверена дополнительно по **разным school.id** в реальных параллельных ответах и тестами запоздавших результатов с разным содержимым.

## 6. Адаптивная и визуальная проверка

Для обеих страниц сохранены `dashboard-{1440,768,390,360}.png` и `calendar-{1440,768,390,360}.png` в `docs/fe002/evidence`. Есть screenshots empty, detail и выбранной школы. `geometry.json` фиксирует viewport, scrollWidth, размеры видимых статических SVG и композиции. **На всех контрольных ширинах горизонтального переполнения нет.**

Windows-браузер резервирует 15 px под вертикальный scrollbar, поэтому фактический clientWidth составляет 1425/753/375/345 при viewport 1440/768/390/360. ScrollWidth не превышает соответствующую доступную ширину. Это объясняет небольшие отличия переносов от Figma без scrollbar. Скрытие системного scrollbar для маскировки разницы не применялось.

Сравнены исходные Figma screenshots: градиент/hero, typography, gaps/radii, desktop/tablet composition, mobile cards/list, type chips, пустая выборка и информационные плашки. В дополнение к необходимым контрактным отличиям добавлены реальные server counts и название школы в блоке последних проектов, явная кнопка поиска и раскрываемые region/date/pagination controls. Эти дополнения обеспечивают запрошенную функциональность, не заменяя UI-kit другим стилем.

Цветные event markers, класс/число учеников/длительность/воспитательное направление в карточках и декоративные примерные сценарии из Figma не подставлены, поскольку соответствующие данные не приходят в используемых ответах. Это зафиксированные ограничения интеграции, а не скрытые pixel-accurate утверждения.
